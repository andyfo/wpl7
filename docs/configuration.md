# Configuration

There are two places a WPL7 install is configured, and they are not interchangeable.

**`deploy/.env`** is provisioning: things a container needs at the moment it starts, or that
a shell script needs before there is a panel. Changing one means re-running
`sudo ./provision/setup.sh`, which is idempotent and exists for exactly this.

**Settings in the panel** is everything else — schedules, limits, defaults, retention. Those
live in the database, take effect immediately, and are editable by anyone who can log in. Who
can log in is not a setting: the accounts are on the panel's **Users** page.

A value that appears in both (the backup schedule, the PHP versions on offer) is seeded from
`.env` on **first boot only**. After that the panel owns it and editing `.env` does nothing.
That is also true of `PANEL_ADMIN_USER` and `PANEL_ADMIN_PASSWORD`, which are read once to create
the owner account. The one exception is asked for by hand: an owner password hash blanked in the
database is seeded again at the next boot, from `PANEL_ADMIN_PASSWORD` if it is set
([troubleshooting.md](troubleshooting.md#forgotten-the-owner-password)).

`setup.sh` **never overwrites an existing `.env`**, and never invents a value that is
missing — it reports it. When a release adds a key, the update's pre-flight lists it as a
warning rather than filling it in with a guess.

## deploy/.env

The file itself is the reference: every key is commented in
[`deploy/.env.example`](../deploy/.env.example), which is what `setup.sh` copies. This is the
map of which ones matter and when.

### What is installed

Maintained by `provision/update.sh`; there is normally no reason to edit these by hand.
[updating.md](updating.md) explains the model.

| Key | |
|---|---|
| `WPL7_SOURCE` | `image` pulls the released panel (the default), `build` compiles it from a checkout |
| `WPL7_VERSION` | What this install reports and compares against releases |
| `WPL7_IMAGE_TAG` | The tag the images were published under — the version, or `edge` |
| `WPL7_CHANNEL` | `stable` follows releases, `edge` the rolling build of `main` |
| `WPL7_PANEL_IMAGE` `WPL7_WORDPRESS_IMAGE` `WPL7_REPO` | Point an install at a fork's images and releases |
| `WPL7_GITHUB_TOKEN` | Optional, read-only. Lifts GitHub's per-address rate limit on the hourly check |

### Identity and TLS

| Key | |
|---|---|
| `PANEL_DOMAIN` | Where the panel answers — and where the links in its emails point (password resets, recovery-email confirmations), and the address AI apps connect to over MCP, which needs it served over TLS ([mcp.md](mcp.md)) |
| `DEV_DOMAIN` | The wildcard subdomain new sites appear under |
| `ACME_EMAIL` | Let's Encrypt account address |
| `TLS_MODE` | `letsencrypt` · `staging` · `none` (local development only) |
| `ACME_RESOLVER` | Which CA issues certificates. **`TLS_MODE=staging` does not pick the staging CA** — this does |
| `SERVER_PUBLIC_IP` | Auto-detected; used for DNS pre-flight warnings |
| `SERVER_ROLE` | `main` (panel + sites) or `worker` (sites only, driven over SSH) |

### DNS

Cloudflare is set up in the panel, under **Settings → DNS** — not here. Its API token there is
the single highest-value change on a busy install: switch on a server's wildcard certificate and
its dev sites share one `*.${DEV_DOMAIN}` certificate issued over DNS-01, instead of one HTTP-01
certificate per subdomain, and Let's Encrypt's rate limits stop being a thing you think about.
The same token lets the panel manage per-site records and publish SPF, DKIM and DMARC from
**Mail → Setup guide**. [dns.md](dns.md).

What is left here: `DNS_PROVIDER`, the provider Traefik's DNS-01 resolver uses — Cloudflare when
empty — with another provider's credentials beside it, and `CF_DNS_API_TOKEN`, a [seed](#seeds).

### Mail

`MAIL_HOSTNAME` is what postfix announces, and it is the name reverse DNS has to match in
direct mode. `SMTP_RELAYHOST` (plus username and password) switches to smarthost mode, which
is what you want unless you have a reason not to — see [mail.md](mail.md).

A name set in **Mail → Setup guide** is written to `/srv/mail/relay.env`, and that file wins
over `.env`; **Reset to default** there removes it. `setup.sh --mail-hostname=` is the way to
overrule it from the command line, and it clears the override so the two cannot fight.

### Storage and database

`SRV_ROOT` (default `/srv`) is where everything persistent lives: `sites`, `mysql`, `backups`,
`traefik`, `panel`, `plugins`, `mail`. Back up that one directory and you have backed up the
install. `MARIADB_ROOT_PASSWORD` is generated by `setup.sh`; `MARIADB_BUFFER_POOL` and
`MARIADB_MAX_CONNECTIONS` are the two knobs worth turning as a box fills up.

### Seeds

`BACKUP_CRON`, `BACKUP_RETENTION`, `WP_DEFAULT_PHP`, `WP_PHP_VERSIONS`, `WP_DEFAULT_LOCALE`
and `WP_DEFAULT_PLUGINS` are read **once**, on first boot. Afterwards they are panel settings.

So is `CF_DNS_API_TOKEN` (with `DNS_PROVIDER` empty or `cloudflare`), read on the first boot that
finds one — an install that kept it here before Settings → DNS existed takes it over on the update
— and `DNS_PROVIDER`, which switches server 1's wildcard certificate on the first time the panel
starts. A token removed in Settings is not seeded back.

## Settings in the panel

Grouped in tabs. Everything on the first five is saved together, by the one **Save settings**
that appears once something has changed — a change waits while you look at another tab. DNS and
Updates act at once, each with its own buttons.

| Tab | |
|---|---|
| **Sites** | Site defaults: PHP version, language, admin email (prefilled in the New Site wizard), default server. Container limits: CPU cores, memory, process ceiling per site container, brought to every existing site at once. FTP & SFTP: on or off everywhere, and the ports |
| **Backups** | Schedule (a field per cron column, with the next three fire times), how many to keep per site |
| **Security** | How often every site's plugins, themes and core are re-read, and whether they are rated against known vulnerabilities. Malware scans: whether every site is scanned, with AMWScan's signatures or not, how often, what happens on a finding, and each scan's memory and time ([security.md](security.md#malware-scans)). Trusted proxies: Cloudflare, and proxies of your own, whose header names the visitor ([security.md](security.md#visitors-behind-a-proxy)) |
| **Mail** | How long mail traffic is kept, the volume per site per hour that flags a site, the (higher) one at which the relay stops accepting its mail, and where operational alerts go: mail suspensions, malware scan findings, and a new release |
| **DNS** | The Cloudflare API token, and each server's wildcard certificate ([dns.md](dns.md)) |
| **Monitoring** | How often sites and servers are looked at, and how long visitor statistics and visitor addresses are kept |
| **Updates** | Version, channel, what is available, and the button ([updating.md](updating.md)) |

A link to one card opens its tab: `/settings#limits`, `/settings#updates`. `?tab=dns` opens a tab.

MCP — whether AI apps may connect at all — is switched on and off on its own page, **Integrations →
MCP**, rather than here ([mcp.md](mcp.md)). So are the default protection of every site (**Sites →
Security**) and automatic blocking, its thresholds and its enforcement (**Servers → Security**); every
security setting and its default is listed in [security.md](security.md#settings).

The container limits under **Sites** are worth understanding before changing: they are what stops
one customer's site from taking the box down, and the defaults (2 cores, 512 MB, 512 processes)
are deliberately generous for WordPress and deliberately finite.

## Where state lives

```
/srv/panel/panel.db       the panel's database - sites, jobs, settings, DKIM keys, the Cloudflare token
/srv/panel/ssh/           the panel's SSH identity for reaching other servers
/srv/panel/update/        state.json and the log of the last update
/srv/sites/<slug>/        one site: wordpress/, config/, logs/
/srv/mysql/               MariaDB
/srv/backups/<slug>/      backups, newest last
/srv/mail/                DKIM keys, sender maps, the credential database
/srv/traefik/             ACME certificates; dns/ holds Traefik's copy of the Cloudflare token
/opt/wpl7/          the install itself: compose files, provision scripts, .env
```

`/srv/panel/panel.db` and `/srv/mail` are the two nobody thinks about until they are gone:
the first is every site's registry and every DKIM private key, and the second is what lets
your customers' mail be signed. [backup-restore.md](backup-restore.md).
