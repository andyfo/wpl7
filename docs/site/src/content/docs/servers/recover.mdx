A server that stops answering, or comes back from a reinstall without its sites, does not take
them with it. Each site can come back from one of its backups. The panel downloads the backup
from its [offsite copy](/docs/backups/offsite/) and builds the site on the server you pick.

<Screenshot name="server-recover" alt="The Recover sites dialog of a server that does not answer, with the backup each site comes back from" />

## Before you start

- An offsite destination with copies of the sites' backups. A backup kept only on the lost server
  is gone with it.
- A server with room for the sites. A rebuilt server can take its own sites back.
- If the panel's own server is the one lost, install the panel again first, as
  [Rebuild the panel's server](/docs/reference/manual-recovery/#rebuild-the-panels-server) shows.

## Recover a server's sites

1. Open the server's page. **Recover sites** is there while the server does not answer, or while
   any of its sites is down. A server that refuses the panel's SSH key answers, so it is not
   offered: its sites most likely still run there. Add the key instead, as after
   [installing the panel again](/docs/reference/manual-recovery/#rebuild-the-panels-server).
2. Choose **Recover sites**, then the **Target server**.
3. Check the list. Each site shows the backup it comes back from, or why it can't.
4. Confirm. The button says how many sites come back.

Each site gets a job of its own. The jobs run one after another on the target server.

## Recover one site

A site whose server does not answer shows **Recover** on its page. So does a site whose container
and database are both gone, which shows as **Missing**. Pick the **Backup** and the **Target
server**, then choose **Recover**.

## What happens

The job downloads the backup onto the target server and checks its checksums. A backup listed
on the target whose folder is gone, as after a reinstall, is passed over for an older one with an
offsite copy. It makes the site's
database and database user, unpacks the files and starts the site. Then it points the site's DNS
records at the new server where the Cloudflare token reaches them, as a [move](/docs/sites/move/)
does. The job log lists the records to change by hand.

On the site's own server, whatever is left of the site is set aside first, and kept for a day.

The site comes back as it was in the backup. Anything written since is not in it.

## When the old server answers again

The panel stops each recovered site's old copy there, and forwards its visitors to the new server.
The copy's files and database stay for a day, so anything written after the backup can still be
copied out. Then they are removed, as after a move.

An email goes to the address in **Settings → Monitoring** when a server has not answered for ten
minutes, and another when it answers again. That one names the sites whose old copies it stops. A
server that has refused the panel's SSH key for ten minutes gets an email that says to add the key.

## Remove the lost server

Recover or delete each of its sites first. A site on a server that does not answer is deleted
without a final backup, and its copy there goes if the server answers again. Then choose **Remove
server** on the server's page. Its backups with an offsite copy stay listed, as **remote only**.
The others are forgotten.

## Limits

- What a site wrote after its last backup is only on the old server.
- For up to a minute after the old server answers, both copies of a site can serve visitors and
  run their scheduled tasks.
- A container app whose backup was taken on another image comes back on the image it runs now,
  with the backup's files and databases. Restore the backup afterwards to go back to its image.
- A container app whose image was uploaded comes back only when that image is on the target
  server. Upload it again first.
- A database added to a site after its last backup does not come back.
- A recovered site can't change server while its old copy is there. The copy goes a day after the
  old server answers again, or with **Finalize now** from then on, or with the server's removal.
- The lost server's mail queue and uploaded plugin zips are gone.
- Sites hosted elsewhere keep their backups on the target server from then on. Their next backup
  there starts over.
